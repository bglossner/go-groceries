# Restaurant orders requirements

Status: selected Cards and tabs implementation, local and unreleased, 2026-11-21. glossner selected Dexie v16 with five tables and the v2 snapshot extension (schema 16 / adapter 2). Applied filters are removable; latitude/longitude fields are removed at glossner's direction and the optional HTTPS Maps link remains. Location defaults are a separate follow-on item.

## 1. Goal and users

Give a household one place to remember restaurants, dishes people enjoyed, and exactly how to order them again. Household members and guests are named on ratings: for example, "Ben 9/10, Sarah 8/10". A person is a display name, not a login or permission boundary. Anyone using the household's writable collection can edit its records and ratings.

The first release is a restaurant notebook, with optional structured ordering details. Ordering, bookings, payments and automatic "what should the household order" suggestions are explicitly out of scope. All requirements below describe proposed behavior; defaults can change during glossner's review.

## 2. User stories and functional requirements

Restaurant story: a household member saves a restaurant with useful tags and general notes, then finds it when choosing dinner.

- **R1 - Navigation:** add a Restaurants entry alongside Meals, Lists and Stores. Opening a saved restaurant directly by its route ID shows the detail; an invalid or deleted ID shows "Restaurant not found" with a route back to the list.
- **R2 - Create:** save a restaurant with a trimmed name of 1-200 characters. Name alone is enough; tags and notes start empty. Reject whitespace-only names. Allow duplicate names for different branches, with a warning on an exact case-insensitive match rather than blocking save.
- **R3 - Edit:** edit the name, tags, general notes and optional location/map details without changing its ID or losing dishes/ratings. Preserve createdAt; update updatedAt only after a successful save. Notes are plain multiline text, up to 10,000 characters, and preserve line breaks.
- **R4 - Delete:** confirmation names the restaurant and counts its dishes and ratings. Cancel changes nothing. Confirm atomically removes the restaurant, its dishes and those dishes' ratings; retain people, reusable tags, shared cached image bytes and remote images. Previously published snapshots/backups remain unchanged.
- **R5 - Restaurant tags:** choose multiple suggested tags or create a custom tag, using searchable autocomplete and chips. Trim names, reject empty names and limit them to 80 characters; reuse tags by trimmed case-insensitive name. Detach a tag from one restaurant without deleting it or changing other restaurants or meals. Defaults and dietary matching follow section 3.
- **R6 - Find restaurants:** case-insensitive substring search matches restaurant names, dish names, country, state/region, city and optional address. Tag filters require all selected tags, with section 3 dietary implications. A person plus an enabled minimum-score filter matches a restaurant with at least one dish at or above that score for that person; default minimum is 8/10, with half-point steps. Selecting a person for sorting alone does not enable this threshold filter. Choosing Household clears and disables the person-score filter; choosing a person again leaves the filter Off until explicitly enabled. Unrated dishes never satisfy it. Search, tags, location and enabled person-score criteria combine with AND. Show applied search, tags, country/state/city, person, enabled minimum score and non-default sort as removable chips above results. Each chip removes only its criterion (R6/R10 dependent resets still apply) and updates the drawer. Clear all restores all restaurants; zero matches shows an empty state. Default order is pinned first, then restaurant name and ID; other modes follow R8.

- **R7 - Pin favourites (core):** toggle a restaurant's pin from list or detail using an accessible Pin/Unpin action; default unpinned. Persist the boolean with the restaurant. A successful toggle updates both views immediately and survives reload, sync and backup restore. Matching pins appear first under every sort, followed by the selected ordering within pinned/unpinned groups. Pins never reintroduce a restaurant excluded by filters/search. Unpin restores normal position; no manual pin order is required. Acceptance checks persistence, immediate position changes and exclusion by filters.
- **R8 - Best-rated sorting (core):** list modes are Name (default) and Best rated, with Household or one person's rating basis. Share the person selector with R6; Household clears/disables the person-score filter, and switching back to a person does not re-enable it automatically. Restaurant rank is its best saved dish: the person's current score, or highest unrounded dish mean for Household. Sort descending within R7's pin groups, then case-insensitive restaurant name and ID; unrated restaurants sort last within their group. Label the dish/score/count determining rank. Detail modes are Category/name (default) and Best rated; Best rated is one ranked list across categories, by person score or unrounded mean, descending, with unrated last and dish-name/ID ties. Scores, person selection, rename/archive/erase and pins refresh ordering without reload. Acceptance: Ben 9 sorts above Ben 8, Sarah selection uses Sarah's scores, ties use name/ID, and missing scores are never zero.
- **R9 - Location entry (core, optional fields):** country, state/region and city are optional trimmed text, each up to 100 characters; address is optional multiline free text up to 2,000. Name alone still saves. State/region or city requires country; city need not have state/region. Recommend free-entry autocomplete from saved values: country across restaurants, state within country, city within country/state including missing-state groups. Match trimmed lowercase text with collapsed internal whitespace, preserve accents, and reuse existing display spelling for a matching key in its parent context. Do not automatically equate US and USA. Refresh suggestions after saves/deletes; permit new values. Changing country refreshes suggestions but retains draft state/city for review, never silently deleting them. No external geography/address parsing is required. Acceptance checks scoped reuse, case/spacing, new values, aliases and absent-state/blank-location entries.
- **R10 - Location drill-down (core):** filters follow Country -> State/region -> City using distinct saved values and R9 normalized keys. Default each to All. State becomes available after a country; City after a state choice, including No state/region. Unknown country matches missing country and disables state/city. Changing country resets state/city filters to All; changing state resets city to All, without editing records. Choices depend only on location parents, independently of other filters. Match exact normalized keys and combine with R6. Acceptance: same city names in different countries/states stay distinct; case/spacing variants reuse choices; All includes missing locations; parent changes, removal chips and Clear all reset dependent selections.
- **R11 - Google Maps link (core, optional field):** store an optional manually entered Google Maps link, up to 2,048 characters, locally validated as HTTPS without username/password. Do not follow it to verify the destination. Open in a separate tab with noopener/noreferrer and no referrer. No embedded map or background geography request. Latitude/longitude fields and Copy coordinates are removed at glossner's direction from the unreleased v16/schema16/adapter2 contract.
- **R12 - Advanced-field visibility (core):** add Show advanced restaurant fields to existing Settings, default Off, as a string boolean in the settings table. Global means all restaurant screens on this device, not a household-synced preference. Off hides price/currency, portion and spice controls/displays; On shows them. Optional menu-photo controls/displays, if implemented, use this switch. Modifiers stay basic because repeat-order wording is central. Name, tags/notes/pins, location/address/maps, dish descriptions/photos, category/dietary/last ordered and all rating fields stay basic. Delivery links are absent from the first release; if added later, they are optional advanced fields, hidden when Off. On does not enable deferred features. Hidden saved values/bytes remain retained, synced and backed up. Visibility changes retain the entire draft, including dirty advanced fields; Save commits that full draft even while advanced fields are hidden. Explicit Cancel/Discard discards the entire draft and leaves saved values unchanged. A basic edit with no advanced changes preserves saved advanced fields. Re-enabling reveals the current draft or saved values as appropriate. This is visibility, not redaction. Setting survives restart, stays excluded from sync/backups and is unchanged by content import; a new device defaults Off. Acceptance: saved price 10 -> draft 12 -> hide -> Save stores 12; the same sequence with explicit Discard leaves 10. Hiding alone retains draft 12, and a later basic edit preserves hidden saved values/image hashes.

Dish story: a household member records a dish, a photo and the wording needed when ordering, then records each person's opinion independently.

- **R13 - Dish CRUD:** add, edit and delete dishes within an existing restaurant. A trimmed 1-200 character dish name is required; all other fields are optional. Duplicate names are allowed for sizes or variants. Prevent saving to a deleted restaurant. Dish deletion confirms its rating count and removes the dish and ratings together; cancel preserves both.
- **R14 - Description and notes:** support separate plain multiline description and personal notes, each up to 10,000 characters. The description explains the dish; notes can say what was good or disappointing. No image or rating is required to save.
- **R15 - Pictures:** allow 0-10 pictures per dish, selected from files or a camera input where supported. Permit removal, reordering, enlargement and selection of one cover picture; default cover is the first picture, and deleting it selects the next or none. Apply the existing compression/cache/R2 path in section 5. On compression, validation, quota or cache failure, show an error, retain the previous saved dish and keep the form available for correction. Uploads must not require connectivity to save locally.
- **R16 - Ordering details:** optionally store price and currency, size/portion, spice level, modifiers, last ordered date and dish category. Price is a nonnegative decimal amount with up to two fractional digits and a required three-letter currency code when price is present; currency selection has no silent default. Portion is free text up to 200 characters. Spice is Unknown, None, Mild, Medium, Hot or Extra hot. Modifiers are multiline text up to 2,000 characters, such as "no coriander, sauce on the side". Category is Unknown, Starter, Main, Side, Drink or Dessert. Last ordered is a valid calendar date, not a timestamp, and cannot be in the future when entered; clearing it means unknown. Price describes the dish, not a bill total.
- **R17 - Item dietary flags:** allow independent Vegetarian, Vegan, Gluten-free option and Dairy-free option flags. Vegan implies Vegetarian for filtering/display. Do not copy restaurant dietary tags onto dishes: a restaurant offering vegan options does not make every dish vegan. Flags are household observations, not verified allergy assurances; an unset flag means unknown.
- **R18 - Dish display:** show saved description, pictures, ordering details visible under R12, dietary flags and notes, plus named ratings and the mean/count from R23. Empty optional values do not display invented defaults. Detail shows "Not rated" when no scores exist. Keep ordering modifiers readable beside the dish name.

Rating story: the household can remember that Ben loved a dish while Sarah would choose something else.

- **R19 - People:** create a person from the rating form or a small people-management flow, then reuse that person by stable ID. Names are trimmed, 1-80 characters, and unique case-insensitively across active and archived people. A matching archived name offers restoration. Do not require an email, age, account or profile image; do not prepopulate real names.
- **R20 - Scores:** save one current rating per dish/person, 1-10 inclusive in steps of 0.5. Require both a person and score; reject 0, 10.5, 8.25, non-numbers and duplicate rows for the same pair. Editing replaces the current score rather than adding a second opinion. Removing a rating leaves the person and dish intact. The UI expresses scores as numbers out of 10, including "Ben 9/10, Sarah 8/10".
- **R21 - Opinion detail:** each person's rating may include a 2,000 character comment and Would order again = Yes, No or Undecided. Missing means Undecided and is not inferred from the score. This belongs to each person rather than a single household flag. Display positive scores as that person's opinion; avoid a separate ambiguous "liked by" list.
- **R22 - Rename/remove people:** renaming updates every displayed attribution without rewriting rating history; reject a duplicate name. Default Remove archives the person: hide from new-rating pickers, retain existing names/scores and mark them Archived; restore makes them selectable again. Historical summaries still include archived people's scores. An explicit Erase person and ratings action previews the rating count and requires confirmation, then atomically deletes the person and all their ratings. Warn that this cannot erase earlier exports or published snapshots.
- **R23 - Summaries:** show each dish's arithmetic mean of current scores, rounded to one decimal, and the number of people rating it; never treat missing scores as zero. Ben 9 and Sarah 8 produces 8.5/10 from 2 people. Include archived people's retained scores. A selected-person view shows that person's score separately from the household mean. Restaurant rows show dish count and the best saved dish under the rating basis in R8, with rating count and a stable dish-name/ID tie break; label it as a dish score, not a restaurant/service review.

Reliability story: the household can use the notebook offline, restore it, and move it through the app's existing sync.

- **R24 - Save/cancel:** restaurant, dish and rating changes save locally and appear without reload. Show field errors and a save error without a false success message. A failed multi-row save rolls back its metadata. Cancelling does not change saved records; leaving a dirty form offers Keep editing or Discard. Preparing images may leave unreferenced cached assets, which remain retained under the existing no-GC policy.
- **R25 - Sync:** include all five proposed metadata tables in the approved snapshot contract and adapters. Metadata-only, pin-only, location/map-only, hidden-advanced-value-only, rating-only, person-rename and image-only changes affect the digest and sync observation, including bulk/collection deletes. The local visibility setting is excluded and does not publish a content change. Publish only after every referenced image has been verified remotely. Import updates restaurant queries and image hydration state without reload. Sync remains whole-snapshot replacement with conditional publication; no row-level merge or simultaneous household editing guarantee is introduced.
- **R26 - Backups/import:** portable exports contain all five tables and all referenced owned image bytes, preserving IDs, relationships, pins, display/normalized location values, Maps links, visible or hidden ordering values, scores, filenames and dish/menu photo order. Visibility settings remain local and unchanged by restore. Restore without R2 access, using staged validation and atomic replacement. Missing bytes, invalid rows, duplicate item/person ratings, invalid foreign keys or unsupported versions leave current data intact. Restore/import that would remove restaurants, dishes, people or ratings must show those changes for confirmation, even when meal names are unchanged. Section 5 defines older backup handling.
- **R27 - Disclosure:** writer sync and full backups contain people's names, ratings and personal notes. Existing read-only links grant remote read access to an entire fixed immutable snapshot and its member images; they cannot publish, write cloud data or read latest through that capability. Recipients can edit and export their imported local copy: the normal app is not a read-only viewer. Permission expiry does not erase downloaded copies. These links do not provide dish-only sharing or field redaction. Before creating such a link containing restaurant data, show that disclosure explicitly, including names, comments, location and hidden advanced values/menu pictures, and allow cancellation. R12 visibility does not remove these fields from the payload. Do not label an existing whole-household link "Share this restaurant". Dish-only, sanitized sharing is a later enhancement; see section 7.

## 3. Proposed restaurant tags

Suggestions are a starter vocabulary, not mandatory classifications. Offer groups in the picker, allowing multiple cuisines/services and custom tags. Seed or offer suggestions idempotently so reopening the page does not create duplicates. Preserve these four exact display labels: **Vegetarian options**, **Vegan options**, **Only vegetarian**, **Only vegan**.

| Group | Proposed tags |
| --- | --- |
| Cuisine | Italian, Indian, Chinese, Thai, Japanese, Korean, Vietnamese, Mexican, Middle Eastern, Mediterranean, American, British, Pizza, Burgers, Cafe/bakery |
| Dietary | Vegetarian options, Vegan options, Only vegetarian, Only vegan, Gluten-free options, Dairy-free options, Halal options |
| Price | Budget, Mid-range, Treat/splurge |
| Service | Delivery, Takeout, Dine-in, Counter service, Reservations recommended |
| Occasion | Kid-friendly, Good for groups, Date night, Quick lunch, Special occasion, Late night, Breakfast/brunch |

Price tags are household judgments rather than automatic currency thresholds. Offer at most one price tag; other groups are multi-select. Absence of a dietary tag means unknown, never "no suitable food".

**Selected relationship to meals:** glossner selected separate `restaurantTags` in the five-table model, reusing the current `tags` pattern of numeric IDs on the owning record, case-insensitive name reuse, autocomplete and chips. Restaurant service labels would otherwise appear in Meals' unscoped tag picker. Keep existing meal tag rows, meanings and IDs unchanged; cuisine/dietary words can coincide without sharing IDs. A future shared/scoped tag redesign would revisit the selected architecture and the meal/shared contracts; it is not an open choice in this proposal.

**Dietary rule:** store the labels explicitly selected, and derive filter implications without adding redundant rows. Only vegan implies Only vegetarian, Vegan options and Vegetarian options. Only vegetarian implies Vegetarian options. Vegan options implies Vegetarian options. Display Only vegan as the most specific badge while explaining the implied matches in picker help. Removing an explicit label removes its derived matches unless another explicit label still implies them. Vegetarian options and Vegan options alone never imply an exclusive restaurant. These labels describe food offerings, not promises about kitchen cross-contact or non-food products; if needed, describe exceptions in notes.

## 4. People and rating model

Use a household-wide `people` table rather than free-text names repeated on every dish. Rating forms select an active name and offer Add person inline. Stable IDs mean a rename updates attribution everywhere, and no extra account/authentication system is needed. A household member may record another person's opinion; this feature does not prove who submitted it.

Recommend half-points on a 1-10 scale, one current rating per dish/person, optional comment and per-person Would order again. No rating history in the first release. Item means are derived, not persisted. Archived people remain in the detail and historical means; an optional Include archived control exposes them in the person filter. Erasure removes their scores from recalculated means. Neither archive nor erasure recalls copies already shared or downloaded.

## 5. Data model and integration proposal

The code at the baseline is authoritative where older architecture docs differ. Dexie is already version 15; image bytes are in `imageAssets` with content-hash references, and v2 sync is implemented. The existing snapshot hard-codes schemaVersion 15 / adapterVersion 1 and a strict table set. Portable imports explicitly recognize versions 12, 14 and 15. Adding a table name alone is insufficient.

**Selected by glossner under the project rule:** retain **version 16** and the five-table model, preserving existing stores. Revised fields, location indexes and optional menu-image slot below remain reviewable details within that model. No schema is changed by this requirements document. Numeric `++id` keys match existing meal/store/tag patterns; no globally unique entity merge is promised.

| Proposed table | Proposed Dexie index string | Fields and relationships |
| --- | --- | --- |
| `restaurants` | `++id, name, updatedAt, *tags, countryKey, [countryKey+regionKey], [countryKey+regionKey+cityKey]` | id, name, tags: restaurantTag IDs, notes, isPinned: boolean (default false), country?, region?, city?, countryKey, regionKey, cityKey, address?, googleMapsUrl?, menuImages?: ImageRef[] (optional, low priority), createdAt, updatedAt |
| `restaurantTags` | `++id, &normalizedName, group` | id, exact display name, normalizedName (trimmed lowercase), group: cuisine/dietary/price/service/occasion/custom |
| `restaurantItems` | `++id, restaurantId, name, category, lastOrderedDate, updatedAt` | id, restaurantId, name, description, notes, images, coverImageIndex?, priceAmount?, currency?, portion?, spiceLevel?, modifiers?, category?, lastOrderedDate?, dietaryFlags[], createdAt, updatedAt |
| `people` | `++id, &normalizedName, status` | id, display name, normalizedName, status: active/archived, createdAt, updatedAt |
| `restaurantItemRatings` | `++id, itemId, personId, &[itemId+personId], [personId+score]` | id, itemId, personId, score, comment?, wouldOrderAgain?: yes/no/undecided, createdAt, updatedAt |

Dates createdAt/updatedAt are stored and serialized as ISO UTC strings; explicitly extend the existing date-converter hooks for new tables if UI interfaces use Date. `lastOrderedDate` is `YYYY-MM-DD`, with calendar validation and no timezone conversion. `priceAmount` is a validated decimal string to avoid accidental rounding. The rating compound unique index prevents duplicate opinions for a pair. `[personId+score]` supports minimum-score lookup; map matching item IDs through restaurantItems to restaurant IDs. Do not denormalize person names or averages into ratings. isPinned is stored but not indexed: Dexie boolean values are not valid index keys. Apply pin/rating ordering to queried metadata. Missing location keys are empty strings so compound indexes include a missing state. Derive keys from display fields with R9 normalization, reuse existing spelling within each parent scope, and validate display/key consistency on saves, snapshots and portable import. Country and compound indexes support the three drill levels. Reuse scoped restaurant rows for suggestions; no sixth location table or external catalog is proposed.

Relationships are enforced by application transactions and import validation, since Dexie does not enforce foreign keys. Validate that every dish owns an existing restaurant, every rating has an existing dish/person and every restaurant tag ID resolves. Enforce the same field limits and pair uniqueness on UI saves, cloud reads/writes and portable import. Multiple edits remain whole-snapshot sync operations; version conflicts need retry/review rather than automatic record merging.

**Selected by glossner under the project rule:** extend the existing **v2 envelope**, with **schemaVersion 16 / adapterVersion 2** and explicit old 15/1 readers. Proposed rows include pins, display/normalized location values, address, Google Maps URL, hidden ordering fields and optional menu-image references. The visibility setting remains outside the contract. Coordinate frontend and Images Worker rollout: old validators reject the new shape, so old clients must not keep writing to a collection after it is upgraded. If safe prevention of older writes needs a separate collection, that remains a rollout fallback for review; do not silently relax the old strict schema.

**Publication compatibility release gate:** old schema15/adapter1 readers do not authorize old writes. Before enabling restaurant publication, separate commit/publish version handling from backward-compatible read adapters. Once a collection has published schema16/adapter2, reject schema15/adapter1 commit and publish attempts, including an old snapshot committed earlier and submitted with the latest valid expectedRevision. The current baseline only conditions publication on revision; it has no schema-downgrade guard. Frontend and Worker must enforce the upgrade rule; rejection keeps the head and all local data unchanged. The implementing worker must prove this before release; the exact guard mechanism is implementation work within the selected v2 extension.

Implementation must update:

- `SNAPSHOT_TABLES` and `SnapshotRows` in the exported shared contract, plus both independently maintained validators: frontend `util/sync/snapshot-validation.ts` and Images Worker `src/image-storage/validation.ts`. Both strict validators must cover shape/version, five tables, pins, location/key consistency, Maps links/text limits, advanced/menu fields, row limits and reference checks; updating shared types alone is insufficient.
- Snapshot normalization, local reconstruction, temporary staging, metadata digest, replacement transactions, change confirmation, query invalidation and hydration. The current confirmation summary mostly compares meal names; add restaurant/dish/person/rating changes rather than implying it already handles them. Date/tag/pin/location/hidden-field-only differences also need replacement confirmation and visible summary counts.
- Image reference discovery everywhere: `getReferencedAssetIds`, snapshot freeze/inventory, runtime snapshot validation and reachability, portable validation/export/import, hydration counts and upload selection must include restaurantItems.images and restaurants.menuImages when present, even while hidden or without a menu editor. Otherwise dish-only/menu-only images can be omitted or rejected as unreferenced. Preserve bounded transfers and asset-first immutable publication.
- `INCLUDE_TABLES` for all five metadata tables, with row validators and version-aware required-table lists in the portable importer. Keep `imageAssets` included in portable backups; keep settings, sync locations, migration/upload jobs and credentials out of the portable data selection. Operational jobs are reconstructed/retained as in the existing importer.
- Existing liveQuery sync observation and mutation hooks where relevant; table-set coverage must catch multi-row saves/deletes as well as simple add/update. No new sync service or dependency is needed merely to include these tables.

**Upgrade and older input:** the v15-to-v16 DB upgrade only creates stores; existing meals, recipes, tags, lists, stores, cached bytes and sync settings remain intact. Default restaurant tables are empty and people are not seeded. The existing settings table needs no schema change; an absent showAdvancedRestaurantFields key means Off. Read old 12/14/15 portable backups and 15/1 snapshots through explicit adapters that supply empty restaurant tables. If local restaurant data would be removed, require a visible replacement confirmation listing counts; automatic sync must not silently clear it. Missing tables in a purported v16 backup are invalid. Unknown/future versions are rejected before touching live data. There is no implicit merge, and IDs/foreign keys must survive round trips unchanged.

**Settings and optional scope:** add proposed key `showAdvancedRestaurantFields`, string values `"true"`/`"false"`, default false, with the existing Settings Switch/query invalidation pattern. Settings is outside SNAPSHOT_TABLES and INCLUDE_TABLES, so this preference adds no sixth shared table. Initialize the complete form draft from the saved row and retain it through visibility changes. Save commits explicit draft changes, including hidden advanced edits, while retaining unchanged hidden fields; do not reconstruct rows from visible controls only or overwrite dirty values with the old saved row. Explicit Cancel/Discard abandons the complete draft, leaving saved data intact. Reserve optional menuImages (0-10 owned references); validate/discover it even if its editor is deferred. Delivery-app links stay outside first-release UI and schema. Later optional deliveryAppLinks would require an approved contract extension, use this switch and retain hidden data. On never unlocks an unimplemented editor.

**Pictures:** reuse `convertFilesToImageBlobs`, `cacheImage`/normalization, `StoredImage` and `useImageUrl`. Persist ordered `ImageRef` asset entries on restaurantItems with a cover index, and optional restaurants.menuImages entries; keep bytes in the shared hash-keyed `imageAssets` cache and per-collection upload inventory. Hash/cache final compressed bytes before a short metadata transaction; recheck the restaurant exists and the saved image references resolve. Never put File/base64/data/blob URL payloads or signed R2 URLs in new dish/menu metadata. Deduplicate identical final bytes, retaining per-slot filename/lastModified. The same verified R2 prepare/complete/commit/publish and download/hydration path used for meals must handle these references. Removing a picture/dish/restaurant must not delete bytes another meal/dish/menu/snapshot uses; retain the current no automatic GC policy.

The current image path targets 1 MiB/1920 pixels when compressing; this target is not a guaranteed bound. Actual new image bytes must meet the existing JPEG/PNG/WebP, 4 MiB, pixel and dimension limits before cloud publication. Core entry uses owned/cached pictures. External image-URL entry can be added later with an explicit offline limitation; no remote mirroring is proposed. After cloud import, show missing-image placeholders and hydration counts until verified bytes are cached, then mark owned images available offline. Browser storage eviction can still remove local copies; a complete backup must fail rather than omit required bytes.

## 6. Screens and flows (words only)

**Restaurant list:** provide name/dish/location/address search, tags, Country -> State/region -> City drill-down, person selection with an optional score threshold, Name/Best rated sorting and Create restaurant. Rows show Pin/Unpin, name, location, tags, dish count and labeled best-dish score/count. Matching pins stay first; missing-state/unknown-country choices remain usable. Applied filters appear as individually removable chips above results, with Clear all. Removing a country resets state/city; removing a state resets city; removing a person disables its score threshold. Parent changes reset dependent filters. Keep filter/sort/person selections while opening/returning from detail.

**Restaurant detail:** show name, pin, tags, location/address, optional Google Maps link, and general notes with edit/delete. Default groups dishes by category, Unknown last; Best rated is one ranked list across categories using Household or a person. Show covers, descriptions, visible ordering details, named scores and mean/count. Add dish opens its form; photo selection uses enlargement. Optional menu pictures are a low-priority advanced section. Archived people stay attributed; include Manage people.

**Restaurant create/edit:** require only name. Provide tags/notes, free-entry scoped location suggestions, optional free-text address, manually entered Maps link. Menu entry appears only if implemented and advanced is On. Save returns to detail; cancel/discard uses existing dialogs/toasts. No embedded map or geography request.

**Item add/edit:** start with name/description/photos, basic modifiers/category/dietary/date fields, then person/score/comment/Would order again rows. Advanced On exposes price/currency, portion and spice; Off retains these values. Add person inline, reject duplicates and preview cover. Save item/ratings together after image preparation. Visibility changes keep the complete draft; Save includes dirty hidden values, while explicit Cancel/Discard abandons the complete draft without changing saved data. Preserve unchanged hidden fields and existing modifiers; deleting a rating affects only that opinion.

**Existing Settings:** add Show advanced restaurant fields, default Off, with help naming hidden fields and explaining retained data. Delivery links are absent in the first release and not unlocked by this switch. It affects every restaurant screen on this device; importing content leaves it unchanged.

| Visibility | Fields |
| --- | --- |
| Basic, always available | Identity/tags/notes/pin; country/state/city/address; Maps link; dish name/description/photos; modifiers; category/dietary/last ordered; person/score/comment/Would order again |
| Advanced, default hidden | Price/currency, portion, spice; menu photos if optional editor is implemented |
| Deferred advanced | Delivery-app links: optional later, hidden when Off; no first-release UI/schema |

Use the app's TanStack file routes, React Query/Dexie reads and invalidation, React Hook Form/Zod, and MUI components already used by Meals, recipe, GroceryList and stores: TextField, Autocomplete, Chip, Dialog, List, Accordion, Select, Checkbox and Button. These are flow descriptions, not a selected layout.

**Project Design rule:** before building any new flow/layout, the implementing worker must offer **2-4 genuinely different mockup options**, each with pros/cons and in every theme the app supports, using the app's components and tokens, together in one captured HTML file. Glossner must select an option before it is built. This documentation task creates no mockups and selects no layout.

## 8. Non-functional requirements and acceptance tests

- **R28 - Offline/PWA:** after the installed app shell is cached, create/edit/search/rate/delete using IndexedDB without network. Previously cached owned pictures render offline after reload; not-yet-hydrated pictures show a placeholder without blocking metadata use. Keep the feature reachable in the existing PWA modes and responsive on mobile; fetching new remote images and cloud sync wait for connectivity.
- **R29 - Accessible UI:** at 360 CSS pixels wide and desktop width, labels/validation and every CRUD/rating action remain usable without horizontal form scrolling. Keyboard users can select tags/people/location filters and sort modes, toggle pins/advanced settings, enter exact numeric scores and confirm/cancel. Give image controls and fields accessible names, restore dialog focus, provide dish-name-based alt text, and never encode scores/status only in colour. Verify every supported theme without adding a theme in this task.
- **R30 - Image/performance limits:** load metadata for search/filter without decoding all pictures. Render list covers lazily, process photo work in bounded batches, release object URLs on cleanup and retain transfer limits. On a documented Chromium test machine with 500 restaurants, 5,000 dishes and 10,000 ratings plus 500 cached photo assets, a warmed list search/filter updates visible results within 500 ms of input; opening a restaurant renders its first 20 dish summaries within 1 second, excluding first-use image decoding. Record machine/browser and timings. This local stress set exceeds the current 10,000 total-record sync cap; do not promise it can be synced as one collection. At current cloud caps (2 MiB metadata, 512 assets, 10,000 total records), stop with an actionable message and preserve local data when limits are exceeded; a cap increase needs contract review.
- **R31 - Scope/dependencies:** use existing app and test dependencies; no new package, server-side CRUD database, authentication provider or paid service unless glossner approves it. Keep tokens, passes and signed transfers out of durable dish/person fields, backups and logs. Render entered text as text, not HTML. No external account or real household data is needed for tests.

## 9. Open questions for glossner

glossner selected Dexie v16 with five tables and the current v2 extension (schema 16 / adapter 2). Those architecture choices are settled; exact revised fields/indexes remain reviewable and no implementation was done. Pinning and per-person sorting are selected core scope, and separate restaurantTags is part of the selected model. Suggestions and first-release delivery links are excluded, not open scope questions.

| Review question | Recommended default | What changes if overruled |
| --- | --- | --- |
| Prior values or a managed location catalog? | Free-entry autocomplete scoped by country/state, normalized case/spacing, no automatic aliases | A catalog adds data maintenance/dependency and missing-region/alias policy. |
| Pins first during Best rated? | Pins first, score sort within each group | Global score sorting may put unpinned restaurants above favourites. |
| Which fields are advanced? | Off by default: price/currency, portion, spice and optional menu photos; modifiers basic; delivery links later only | Different grouping changes visibility without deleting data. |
| Sync advanced visibility between devices? | Local setting; content imports keep it | Sharing needs a selective settings contract change; never export credentials wholesale. |
| Menu editor alongside core? | Allowed optional, low priority; preserve menuImages in data/sync even if editor deferred | Earlier editing adds UI/tests; deferral keeps first forms smaller. |
| Only vegan imply Only vegetarian? | Derived implication, most-specific badge | Independent meanings change filters/help. |
| Whole scores or halves; opinion history? | 1-10, halves, one current opinion | Whole scores reduce precision; history adds order/time records. |
| Removing a person? | Archive default; explicit erase deletes ratings | Immediate deletion loses attribution and changes means. |
| Restaurant-only sharing in the first release? | Defer sanitized sharing; disclose full-snapshot scope | Earlier sharing needs an approved projection and privacy tests. |
| Later-extra priorities? | Usual-order copy, then menu URL/phone; menu photos low priority | Changes later scope, not selected core pin/sort/location. |
